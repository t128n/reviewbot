# Reviewbot v1.1 Implementation Plan

**Status:** Implemented
**Specification:** `docs/specs/v1.1.md` (incremental to `docs/specs/v1.0.md`)
**Last updated:** 2026-11-13

## 1. Scope

v1.1 completes the duplicate-issue lifecycle and changes the public response policy from a
report format to decision-first GitHub prose. It is additive to v1.0. The only superseded
v1.0 rules are the ones named in `docs/specs/v1.1.md` §1:

- duplicate-related label changes and duplicate closure/reopening;
- duplicate-only follow-up monitoring without an authorized `/rb` command;
- persisted `due_at` checks inside the existing poll/worker loop;
- one prompt at `src/prompt.md`, updated in place.

Everything else stays intact: single worker, outbound polling, App authentication,
read-only automatic OpenCode sessions, authorization for explicit tasks, no automatic code
changes, no new CLI commands, no extra infrastructure, no per-repository configuration.

## 2. Design decisions

The material decisions are recorded in `docs/adr/0009-duplicate-lifecycle.md`.

Summary:

- OpenCode returns an **advisory** structured decision plus issue-specific prose. The daemon
  validates references, canonical selection, closure eligibility, and every transition. A
  duplicate proposal missing a canonical issue, matching evidence, or (for `likely_duplicate`)
  a targeted question degrades to non-closing triage instead of failing or inventing text.
- Discovery is bounded and deterministic: direct issue references first, then at most three
  GitHub search queries and 20 retrieved candidates. Search failure means "no duplicate",
  never an invented one.
- One durable `duplicate_cases` row per `(repository_id, issue_number)`. Job keys remain the
  existing queue's idempotency mechanism.
- Notices, closure comments, corrections, and labels are published through the existing
  `Publisher` with stable HTML markers and pre-write installation/state revalidation.
- Deadline checks are ordinary jobs enqueued by the repository poll when `due_at` is reached.
  No scheduler or second loop is introduced.
- Lifecycle transitions are deterministic code. The model may recommend `distinct`,
  `still_duplicate`, or `uncertain`; code decides whether that recommendation is allowed to
  cancel, renew, close, or reopen.
- Explicit tasks are triggered by the literal `/rb` command, not the installed App mention.
  Detection uses a token boundary; write-access authorization and duplicate-only follow-ups
  stay unchanged.

## 4. Lifecycle and failure handling

```text
triage decision
  independent / related  -> v1.0 triage comment, no case
  confirmed / likely     -> intent (notice_pending) -> notice -> pending(due_at)
pending at due_at        -> re-fetch issue/canonical/comments
  maintainer override    -> cancelled
  substantive reply      -> duplicate-comment job -> distinct | still_duplicate | uncertain
  GitHub state conflict  -> cancelled
  otherwise              -> closure comment -> close(state_reason=duplicate) -> closed
closed                   -> reporter/write follow-up -> reopen only if bot-closed and distinct
```

Crash and retry rules:

- The case intent (including the validated decision and notice text) is persisted before the
  first GitHub write. A retry or post-restart reconciliation republishes with the same
  revision marker and therefore cannot duplicate a notice.
- The 24-hour clock is set only after GitHub confirms the notice. `notice_pending` cases are
  reconciled by the poller, so an unpublished intent never becomes due.
- Closure posts one marker-backed comment, then closes. If the close fails, retry finds the
  comment marker and only retries the state change.
- SQLite state never authorizes closure by itself: the issue, canonical issue, installation,
  and comments are re-read immediately before the transition.
- Rate limits, 5xx responses, and revoked access keep the job retryable; failed deadline
  checks back off and stop automatic retries after three attempts, while a permanently
  failed comment reassessment is not re-enqueued for the same comment. The issue is left open
  rather than closed on unresolved evidence.
- Before closure the daemon re-resolves the canonical chain. If the verified original moved,
  it publishes a fresh notice and grants a new 24-hour window instead of closing onto a stale
  duplicate placeholder.
- A human close, reopen, cancel, or canonical deletion cancels the case. Cancelled cases are
  never re-armed automatically. A maintainer override on a bot-closed duplicate reopens it
  once and removes the bot-applied duplicate label.

## 6. Verification strategy

Deterministic tests use an in-memory SQLite store and fake GitHub/OpenCode collaborators.
Time is injected; no test waits 24 hours.

- Discovery: explicit references, unrelated references, search bounds/failure, closed
  canonical handling, PR candidates, cycles and chains.
- Classification: confirmed, likely, related, independent; downgrade when canonical is
  invalid/inaccessible/self/circular; titles alone are never sufficient.
- Lifecycle: notice intent, one notice, 23h59m stays open, 24h closes once with the duplicate
  state reason, label provenance, maintainer override, generic thanks, material distinction,
  renewal, cancellation, bot reopening, human reopen, human close, inaccessible canonical,
  restart boundaries, API failure/recovery.
- Security: duplicate text cannot choose labels/deadlines/hosts or mutate without
  authorization; automatic sessions keep the v1.0 read-only ruleset.
- Compatibility: the full v1.0 unit suite, type check, and `doctor`/`status` smoke checks.

Live GHE.com acceptance (App permissions, `state_reason`, labels) still requires the
configured test organization and is recorded separately; unit tests alone are not claimed as
live verification.

Local verification performed:

- `bunx tsc --noEmit` passes.
- `bun test` passes: 185 tests across 15 files, including the v1.0 regression suite and the
  response-example selection and phrasing checks.
- `reviewbot doctor` passes on the configured `github.com` App/OpenCode environment:
  credentials, installation permissions, repository access, OpenCode compatibility, SQLite,
  workspace storage, and the read-only/implementation permission probe are all enforced.
- No duplicate lifecycle mutation was exercised against a live repository; label creation and
  `state_reason=duplicate` remain external acceptance items.

## 7. Deviations and limitations

- Canonical selection follows verified bot-managed duplicate chains and explicit
  "duplicate of #N" text, with cycle and depth guards. It does not perform semantic
  cross-repository deduplication.
- A closed canonical issue only supports `confirmed_duplicate` when the reporter explicitly
  referenced it; otherwise the decision degrades to `related` so a regression is not
  silently closed.
- Notification of cancellation is limited to cases that already published a notice. Label
  API failures are logged and surfaced in `status`, never turned into repeated issue noise.
- Comments that arrive after the final pre-close read but before GitHub processes the close
  can only be handled by the post-closure reassessment path.
- Deadline retries stop after three failed attempts and remain visible in `status`; a new
  comment or operator investigation can still move the case forward.
- Direct references are fetched before search and are not counted against the 20-candidate
  search bound. A safety cap of 10 direct references per issue bounds untrusted input; later
  references are ignored rather than expanding API cost without limit.
- Live App-permission behavior for label creation and `state_reason=duplicate` remains an
  integration-test item.
