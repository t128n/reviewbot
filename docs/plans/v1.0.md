# Reviewbot v1.0 Implementation Plan

**Status:** Implemented; external GHE.com acceptance tests pending credentials
**Specification:** `docs/specs/v1.0.md`
**Last updated:** 2026-11-13

## 1. Scope and invariants

Reviewbot is an integration layer between GitHub and an existing OpenCode V2 service. It
owns GitHub authentication, discovery, authorization, durable jobs, workspace preparation,
dispatch, validation, and publication. OpenCode owns reasoning, tools, models, and session
execution. GitHub remains authoritative for repository and PR state; OpenCode remains
authoritative for sessions.

Non-goals from the specification are binding: no custom agents/modes, no model management,
no dashboards, no webhooks, no workflow engine, no parallel workers, no automatic merges,
no approvals, no sandbox provisioning, no per-repository configuration.

## 2. Architecture

```
src/
  cli.ts        Commander commands: setup, run, status, doctor
  config.ts     paths, Valibot config/credentials schemas, host validation
  db.ts         SQLite schema, WAL, store and job transitions
  github.ts     App auth, manifest flow, narrowed installation clients, API helpers
  polling.ts    per-repository cursors, discovery, baseline, dedupe
  jobs.ts       job kinds, payload schemas, enqueue keys
  worker.ts     single worker, timeouts, retries, recovery, dispatch
  opencode.ts   service discovery, compatibility, sessions, permissions, results
  workspace.ts  mirror clones, clean wrapper worktrees, git auth, integrity checks, commit/push
  related.ts    bounded related issue/PR context for triage
  publish.ts    triage/review/reply publication, markers, inline validation
  setup.ts      interactive manifest wizard, installation wait, baseline
  security.ts   permission enforcement probe and gate
  prompt.md     versioned instruction text
  log.ts        Pino logger with redaction
test/           bun test unit tests
```

## 3. Persistent state

SQLite (WAL) at `<data>/reviewbot.db`:

- `installations`, `repositories`: installation/repository observation state and cursors.
- `pull_state`: last observed head, draft state, last reviewed head.
- `sessions`: GitHub issue/PR → OpenCode conversational session mapping.
- `jobs`: durable queue with stable unique keys, attempts, retry time, errors.
- `reviewed_heads`: commit SHAs already reviewed per PR.
- `publications`: idempotency markers and GitHub identifiers.
- `findings`: hashed published findings for duplicate suppression.
- `meta`: bot identity, security gate result, poll state.

No conversation transcripts, OpenCode histories, or credentials are stored.

## 4. Behavioral contracts

### Trigger contract

| Trigger | Job |
| --- | --- |
| New issue created after repository baseline | `triage` |
| New non-draft PR created after baseline | `review` (initial) |
| Non-draft PR head changed since last observation | `review` (incremental if previously reviewed) |
| Draft PR becomes ready | `review` (initial if not reviewed) |
| Comment/review reply mention from user with write+ | `conversation`, or `fix` when the instruction requests changes |
| Bot's own events | ignored |
| Edits to title/body/labels alone | ignored |

New repositories/installations set cursors and PR baseline at discovery time; historical
issues and PRs are not processed. Comments created at or before baseline are ignored.

### Permissions

Automatic sessions use a default-deny ruleset allowing only `read`, `glob`, `grep`; external
directories, edit, shell, execute, subagent, skill, webfetch, websearch, question, and MCP
tools remain denied. Implementation sessions additionally allow `edit` inside the
workspace. A startup probe must resolve both the read-only and implementation rulesets as
`enforced` before automatic jobs run; otherwise the gate fails closed and jobs remain
queued.

### Publication

- Triage: exactly one issue comment per issue, with an HTML marker.
- Review: one `COMMENT` review per PR head, with inline comments only on changed lines;
  unmappable findings are demoted to the summary; a short review is posted when clean.
- Replies: issue comment, or inline reply for inline review discussion, with markers.
- Fixes: new branch + draft PR + notification comment linking the source; contributor
  branches untouched.
- Every write revalidates installation access and, for requested work, the requester's
  current permission. PR reviews revalidate the head SHA and discard stale results.

## 6. Verification strategy

- `bun test` unit coverage: host/config validation, mention detection, diff line mapping,
  job dedupe/transitions, result parsing/validation, permission rules, rate-limit parsing,
  publication marker/idempotency logic.
- `bunx tsc --noEmit` type check (passes, clean).
- `bun test` unit suite (85 tests passing across 11 files).
- `bun run src/cli.ts doctor` against the local environment for Bun/Git/SQLite/OpenCode.
- Credential file ACL verified on Windows with `icacls`: the test file granted access only
  to the current user.
- Live OpenCode probe: session creation, permission decisions, service compatibility, and
  session instruction entries verified against OpenCode 2.2.7. The read-only gate is
  deterministic and does not use a model. A live session with an explicit test model was
  denied an external read (`permission.rejected: external_directory`).
- Deterministic OpenCode permission probe for both rulesets: read-only allows
  read/glob/grep and in-workspace reads; implementation adds workspace edit. Both deny
  shell, execute, external directory, network, subagent, skill, question, MCP, and
  Reviewbot credential/database access.
- Session-root isolation verified against OpenCode 2.2.7: project config in a child
  checkout is not loaded when the session root is the clean wrapper.
- GHE.com acceptance tests (AC-01…AC-20) require a test organization, App installation, and
  model quota. They are recorded as pending, not claimed as passing.

## 8. Known limitations and outstanding work

- GHE.com manifest conversion, installation auth, and all publish paths require live
  credentials and are not claimed as verified.
- Full task execution requires a working OpenCode model. The local default provider
  returned `provider.quota`; the security gate is independent of that and verified.
- Sessions use a clean wrapper directory so repository-local OpenCode config, plugins,
  MCP definitions, and skills are not loaded (ADR 0007); repository instructions are data,
  not configuration.
- Issue/comment polling windows carry a changing `since` value, so conditional requests are
  used for the stable open-PR list; other sources rely on bounded overlap and job dedupe.
- Permanently failed jobs remain failed until a repeated trigger or operator action; there
  is no retry command in the four-command CLI.
- After an ambiguous review publication is recovered by marker, the head is marked
  reviewed without re-recording finding hashes from the unpublished model result; duplicate
  suppression may be less complete for that head.
- Global OpenCode configuration and plugins are trusted operator configuration. Session
  permission decisions are verified, but operator-installed plugins are not audited.
- Tests are not executed for untrusted repositories; fix PRs explicitly report this.
- GitHub App rate-limit and secondary-limit behavior is implemented but not load-tested
  against a live enterprise organization.
