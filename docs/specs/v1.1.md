# Reviewbot — v1.1 Product & Technical Specification

**Status:** Implemented (external GHE.com acceptance pending credentials)  
**Version:** 1.1  
**Date:** 2026-11-13  
**Baseline:** `docs/specs/v1.0.md` (fully implemented)  
**Target:** GitHub.com and GitHub Enterprise Cloud (`*.ghe.com`)  
**Runtime:** Existing Bun / TypeScript daemon, GitHub App, SQLite, and OpenCode V2 integration

## 1. Product decision

**v1.1 makes Reviewbot an issue-triage agent that can complete the duplicate-issue lifecycle, rather than merely describe a duplicate in a long investigation.** It also changes the communication policy from a rigid investigation report to a concise, decision-first GitHub response.

Required outcomes:

1. Identify existing issues before duplicating an investigation.
2. Distinguish confirmed duplicates, likely duplicates, related issues, and independent issues.
3. Identify the canonical issue and direct discussion there.
4. Apply narrowly scoped duplicate-triage labels.
5. Notify the reporter of a **24-hour opportunity to explain a material difference**.
6. Automatically close eligible duplicates after that window, with GitHub's `duplicate` state reason.
7. Stop or reverse the automated workflow when new evidence or a maintainer decision warrants it.
8. Generate proportionate, GitHub-native comments without losing the evidence standards of v1.0.

Reference behavior: [OpenCodeJR's handling of anomalyco/opencode#63249](https://github.com/anomalyco/opencode/issues/63249). This is a behavioral reference, not a dependency or a requirement to copy its implementation.

### Normative relationship to v1.0

This document is an **additive v1.1 specification**, not a replacement architecture. All v1.0 requirements remain in force **except the explicit overrides below**.

| v1.0 provision                                      | v1.1 change                                                                                                                 |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| §6: triage cannot change labels or close issues     | Permit **only** duplicate-related labels and duplicate closure/reopening under this specification.                          |
| §6: subsequent responses require authorized mention | Permit **only** duplicate-specific follow-up monitoring, clarification, and status comments without an `/rb` command.      |
| §8: explicit tasks use installed-App mentions       | Replace the trigger with the literal `/rb` command. Comment and inline-review discovery, authorization, and session rules stay unchanged. |
| §5: no schedules or arbitrary event rules           | Permit persisted `due_at` checks for pending duplicate closures in the **existing poll/worker loop**. No general scheduler. |
| §16: label management and issue closure excluded    | Narrow exception for duplicate lifecycle only; other issue-management functions remain excluded.                            |
| §10: one prompt at `src/prompt.md`                  | Update that file in place. No additional personalities, named modes, or prompt-template engine.                             |
| §12: existing queue, idempotency, recovery          | Extend these mechanisms with minimal duplicate-case state. Do not replace them.                                             |

**Unchanged:** single worker, outbound polling, existing OpenCode service, read-only automatic agent execution, GitHub App authentication, collaborator authorization for explicit tasks, no automatic code changes, no auto-merges, no new CLI commands, no additional infrastructure, and no per-repository configuration.

### Authorized command trigger

v1.1 replaces the installed-App mention trigger for explicit tasks with the literal `/rb` command. The command is case-insensitive and must stand alone at the start of a comment or after whitespace. `@reviewbot`, path fragments such as `src/rb`, and longer tokens such as `/rb-extra` do not trigger work.

Command detection replaces only the old mention check. Comment and inline-review discovery, write-access authorization, duplicate-only follow-up handling, session continuity, and publication rules stay unchanged. Replies without `/rb` still cannot start ordinary conversation or implementation tasks.

## 2. Scope and non-goals

### In scope

- Duplicate discovery and cross-issue comparison within the same installed repository.
- Selection of an authoritative/canonical issue.
- Initial duplicate notice, pending-close label, 24-hour grace period, final duplicate closure, and reporter follow-up.
- Reassessment, cancellation, and limited reopening when a bot-closed duplicate is shown to be distinct.
- Adaptive response style for **existing issue triage and PR review output**, without changing PR review decisions or permissions.
- Structured triage output, durable duplicate-case state, tests, and diagnostics using existing components.

### Explicitly out of scope

- Automatic resolution of ordinary issues, stale-issue cleanup, arbitrary close policies, inactivity timers, or generalized workflows.
- Changes to labels unrelated to duplicate triage; assignees, milestones, projects, issue titles, or issue bodies.
- Closing PRs, modifying PR review states, resolving review threads, auto-approving, or auto-merging.
- Automatically fixing the root issue or generating a PR just because a duplicate was detected.
- Cross-repository duplicate management, fuzzy deduplication infrastructure, vector stores, embeddings, search indexes, or new databases.
- Independent LLM agents/modes, per-repository policies, template engines, model routing, a scheduler service, and webhooks.
- Rewriting Git history or automatically expanding an issue into unrelated cleanup tasks.

## 3. Duplicate discovery

### 3.1 Required context

Before a new issue is independently investigated, the triage task must inspect:

1. Its title, body, and relevant existing discussion.
2. Explicit issue references (e.g. `see #1`, `duplicate of #1`, or a GitHub issue URL).
3. A bounded set of relevant existing issues from **the same repository**, including open and closed issues.
4. Candidate issue bodies and relevant comments before deciding that they describe the same underlying problem.
5. Relevant PRs only where needed to determine whether the canonical issue already has a fix or a meaningful different scope.

Fetch valid explicitly referenced issue numbers first; do not depend on search indexing for direct references. Use GitHub's existing API/search facilities, not a local semantic index. Exclude the current issue and bot-created loops. Bound discovery to at most **3 search queries and 20 retrieved candidate issues** per initial triage, plus direct references; inspect the highest-value candidates first. If search is unavailable or incomplete, do not invent a duplicate.

### 3.2 Classification contract

| Classification        | Required evidence                                                                                                                                                | Behavior                                                                              |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `confirmed_duplicate` | Same underlying report, with direct corroboration (e.g. explicit reference plus matching description, reporter confirmation, or indistinguishable reproduction). | Post concise duplicate notice, label pending closure, start 24-hour window.           |
| `likely_duplicate`    | Strong match in affected component, actual symptom, and relevant conditions; a meaningful distinction is not established.                                        | Explain the match, **ask what differs**, label pending closure, start 24-hour window. |
| `related`             | Similar component/symptom, but different behavior, cause, version scope, or insufficient evidence to call it the same report.                                    | Link related issue; **do not** start automatic closure.                               |
| `independent`         | No defensible duplicate candidate.                                                                                                                               | Perform ordinary v1.0 investigation; **do not** start automatic closure.              |

A shared keyword, similar title, or model confidence assertion alone is insufficient for `likely_duplicate`. A directly cited issue number also is **not by itself** proof: compare the actual content. An issue with plausible unresolved distinguishing evidence must be classified `related` or left pending clarification **without** a closure deadline.

### 3.3 Canonical issue selection

- Prefer the issue explicitly identified by the reporter if it covers the same report.
- Otherwise prefer the earlier, substantive issue where reproduction, investigation, discussion, or fix is already tracked; do not select solely by lowest issue number.
- Follow an existing duplicate's canonical reference where verified, so chains converge on the original; detect cycles, broken references, and inaccessible targets.
- Never designate the current issue, an unrelated issue, or a closed duplicate placeholder as the canonical source when a valid original is available.
- A completed/closed original may still be canonical **only** if the report is the same resolved incident. A plausible regression or new version-specific failure must not be silently discarded as a duplicate.
- If canonical selection is ambiguous, **do not automatically close**; ask for clarification if useful.

## 4. Duplicate lifecycle

### 4.1 State machine

```text
                  independent / related
new triage ---------------------------------> ordinary v1.0 triage
    |
    | confirmed / likely duplicate
    v
pending_duplicate -- new distinguishing evidence --> reconsidering
    |                                               |      |
    | 24 h elapsed; checks pass                     |      +--> pending_duplicate (new notice/deadline)
    v                                               +---------> cancelled (leave open)
closed_duplicate -- substantiated follow-up ------> reconsidering
    |                                                        |
    +<------------------- still duplicate -------------------+
                                                             |
                                                             +--> reopened_distinct

pending_duplicate -- maintainer override / state conflict --> cancelled

notice_pending -- successful notice reconciliation --> pending_duplicate
```

`pending_duplicate`, `closed_duplicate`, `cancelled`, and `reopened_distinct` are durable case states, **not** new agent modes. Reconsideration is an ordinary queue task using the existing triage session/context.

### 4.2 Initial decision

For `confirmed_duplicate` or `likely_duplicate`, in order:

1. Re-fetch the current issue and canonical issue to verify they exist, are accessible, and remain eligible.
2. Persist a unique **notice-pending intent** with the issue number and proposed canonical reference before any GitHub write.
3. Publish **one** concise notice linking the canonical issue, explaining the meaningful match, and stating that Reviewbot intends to close this issue **in 24 hours** unless the reporter supplies a material distinction. Reconcile the intent and existing publication marker on retry.
4. Persist the actual notice identity, classification, canonical reference, and `due_at = notice_posted_at + 24 hours`; transition the intent to `pending_duplicate`.
5. Add the fixed `pending close` label (see §5); never block the notice solely because labeling fails.
6. Leave the issue **open** throughout the grace period.

The 24-hour clock begins only when GitHub confirms publication of the notice. An unpublished intent never becomes due for closure.

For `likely_duplicate`, the notice must explicitly invite a specific difference in behavior, reproduction, environment, or expected result. Do not copy a full technical investigation into the duplicate issue. Keep substantive findings and the fix discussion on the canonical issue.

### 4.3 Deadline processing

The existing poll/worker loop discovers due cases. No cron job, second daemon, or generic scheduler is introduced. At or after `due_at`, Reviewbot must:

1. Re-fetch the duplicate issue, canonical issue, and comments created since the notice/checkpoint, using complete pagination.
2. Verify the issue is still open and the canonical relationship still holds.
3. Check for new, material distinguishing evidence, a reporter objection that requires investigation, or a maintainer override.
4. If relevant evidence exists, **pause closure and reassess**; if evidence contradicts the match, cancel the duplicate case. If the match remains defensible after a substantive reassessment, publish an updated notice and set a new 24-hour deadline.
5. If a maintainer explicitly asks to keep the issue open or rejects the duplicate decision, cancel the deadline without attempting to override that decision.
6. Otherwise publish a short final explanation, then close the issue with `state=closed` and `state_reason=duplicate`.
7. Remove the bot-managed `pending close` label and apply `duplicate` where possible. Keep the final GitHub state and persisted case synchronized.

The deadline is **not** permission to close without re-checking GitHub. Closure must not happen before the 24-hour interval has elapsed. Polling and backoff may make it later.

A generic `thanks`, an emoji, or an unrelated comment does not automatically reset the timer. A substantive reply identifying a difference, or an explicit objection from the reporter, **does** block silent closure pending reassessment—even if the reporter lacks repository write permission. Such a reply is evidence for this workflow, not authorization to run arbitrary instructions.

### 4.4 After closure

- Follow-up comments by the original reporter or a collaborator with write access may trigger **duplicate-only** reassessment without an `/rb` command.
- If new evidence demonstrates a materially different issue, Reviewbot may reopen **only an issue it closed under this duplicate workflow**; publish a short correction and remove bot-owned duplicate labels.
- If the case remains a duplicate, explain why and link the canonical issue once; do not repeatedly post the same determination.
- Never reopen an issue closed by a human or another automation. Never automatically re-close an issue that a human has reopened or explicitly kept open.
- Ordinary natural-language requests, code changes, PR work, and unrelated follow-ups still require an authorized `/rb` command.

### 4.5 Cancellation and conflicts

Cancel or suspend automated closure when:

- A maintainer explicitly overrides the duplicate decision.
- The issue is manually closed, reopened, transferred, or otherwise changed in a way that invalidates the case.
- The canonical issue is deleted, inaccessible, or no longer a defensible original.
- The bot loses installation access, the required issue-write permission, or current GitHub state cannot be verified.
- A pending clarification or uncertainty cannot be resolved safely.

Never fight human state changes or automatically re-arm a cancelled case. A new authenticated maintainer instruction may initiate a fresh investigation under the `/rb` command and authorization rules.

## 5. Label policy

Only two fixed labels belong to v1.1:

| Label           | Meaning                                                                 | When applied                                                |
| --------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------- |
| `pending close` | Proposed duplicate; 24-hour explanation window active.                  | Initial `confirmed_duplicate` or `likely_duplicate` notice. |
| `duplicate`     | Issue closed by Reviewbot as a duplicate of a specific canonical issue. | Successful duplicate closure.                               |

- Use GitHub's standard label APIs; add labels without replacing unrelated labels.
- Create **only these two labels**, on demand when missing and when the GitHub App has permission. Do not change existing label colors/descriptions or any repository policy.
- If label creation or application is forbidden, continue the issue workflow and report the limitation through existing diagnostics, without repeated issue-comment noise.
- Remove `pending close` on closure/cancellation; remove `duplicate` on a justified bot reopening **only if applied by Reviewbot**.
- Store enough provenance to avoid removing unrelated or pre-existing labels. Other label management stays prohibited.
- GitHub's `state_reason=duplicate`, issue relationship, and comments are the authoritative closure record; labels are supplementary.

## 6. Response style and output quality

### 6.1 Core policy

**Decision first. Detail proportional to risk. Action rather than report formatting.**

- State the conclusion or the information needed in the opening sentence.
- Favor one short, natural GitHub comment over fixed headings such as `Assessment / Evidence / Uncertainty / Next step`.
- Use concise paragraphs and targeted bullets when they improve scanning; use a table only for genuinely comparative findings.
- Keep evidence directly relevant to the decision. Link existing investigation or code rather than repeating full file inventories in a duplicate issue.
- Clearly distinguish verified facts, inferences, and unknowns. Never say `confirmed` about a Git index entry that could not be inspected directly.
- Mention adjacent findings only if material; do not silently expand ZIP cleanup into compiler outputs, Javadocs, or Git-history rewriting.
- Propose the smallest actionable next step. Do not ask a question unless the answer changes the immediate decision or authorized implementation.
- Do not write pleasantries, generic praise, disclaimers for their own sake, invented certainty, or internal agent-process narration.
- Respect the issue's language where practical. GitHub Markdown, links, file paths, and code blocks must be readable.

Investigation depth does not determine public comment length. Lead with the current conclusion, include only the evidence needed to support it, state uncertainty when it changes the diagnosis, and ask the smallest number of questions needed to move forward. Offer diagnostic commands only when they materially help the reporter. Before publishing, remove every sentence that does not improve the reader's understanding or the next action.

These are **soft length targets**, not a hard truncation policy:

| Situation                                | Typical size                                                                           |
| ---------------------------------------- | -------------------------------------------------------------------------------------- |
| Confirmed duplicate                      | 2–5 sentences.                                                                         |
| Likely duplicate                         | 3–6 sentences, including a targeted distinction question and 24-hour notice.           |
| Routine issue triage                     | 1–3 short paragraphs, optionally a few bullets.                                        |
| Complex investigation / security concern | As much evidence as needed to support a consequential conclusion, without boilerplate. |
| Clean PR review                          | One brief assessment; no fabricated findings.                                          |
| PR with actual defects                   | Concise overview plus existing v1.0 inline findings.                                   |

Do not weaken v1.0 review correctness, inline mapping, or severity requirements just to make responses shorter. Do not introduce custom templates or agent personalities: update the existing `src/prompt.md` and validate a small set of structured result fields.

### 6.2 Example: explicit duplicate

Issue **#2** says `see #1`; the two reports describe the same committed ZIP archives.

> This is a duplicate of #1. Both reports concern generated ZIP archives committed under `2026-ws/vfhgp1/`, and #1 already tracks the investigation and proposed cleanup.
>
> Please follow #1 for updates. I'll close this issue as a duplicate in 24 hours unless you reply with a material difference between the two reports.

`pending close` is applied; #2 stays open for 24 hours. There is no repeated ZIP inventory, no scope-expansion question, and no unsupported claim about Git index state.

### 6.3 Example: strong suspected duplicate

> This looks like the same issue tracked in #123: both reports describe the menu remaining open after switching tabs on Windows.
>
> Is your case different in the affected menu, reproduction steps, or application version? If so, please explain. Otherwise I'll close this as a duplicate in 24 hours; updates to the shared problem belong in #123.

### 6.4 Example: closure

> Closing as a duplicate of #1. The reports describe the same committed ZIP artifacts, and no distinguishing issue was established during the 24-hour response window. Please continue the discussion in #1.

The wording is illustrative, not a runtime string-template system. Fixed daemon-generated deadline/closure disclosures are permitted; issue-specific technical rationale comes from validated OpenCode output.

### 6.5 Task-specific phrasing references

`src/prompt.md` remains the single shared instruction entry point. Static plain-text examples
live in `src/prompts/*.txt` and Reviewbot appends only the sets relevant to the current task:

| Task | Example files |
| --- | --- |
| New-issue triage | `duplicate-confirmed`, `duplicate-likely`, `issue-investigation`, `issue-clarification` |
| Duplicate reassessment | `duplicate-closed`, `duplicate-reopened` |
| Pull request review | `pr-review` |
| Authorized conversation | `conversation` |
| Authorized implementation | None; the shared instructions apply |

Selection uses the known job kind, never a model-chosen workflow. The examples are behavioral
references, not templates: their issue numbers, paths, symptoms, and findings must not be
reused. Investigation depth stays independent of public comment length, and a duplicate
comment references the canonical issue's existing investigation instead of reproducing it.

The daemon appends deadline, closure, cancellation, and reopening disclosures. The example
responses therefore show only the model-authored portion and never grant the model authority
to state a deadline or claim a lifecycle action.

## 7. Implementation contract

### 7.1 Responsibilities

**OpenCode (existing read-only task execution):** search and compare issue evidence, select a proposed classification and canonical issue, identify material differences, generate the concise technical rationale, and reassess new comments.

**Reviewbot daemon:** validate candidate issue references, enforce lifecycle policy, decide whether closure/reopening is authorized, manage fixed labels, persist deadlines, re-check GitHub, publish notices, and perform state transitions with installation credentials.

The LLM's output is **untrusted advisory data**; it must never be treated as authority to call GitHub mutation APIs. No GitHub credentials, issue-write tools, or shell execution are passed into automatic OpenCode tasks. Maintain v1.0's fail-closed execution requirements.

### 7.2 Structured triage result

Extend the existing v1.0 result schema rather than implementing a new agent protocol. Illustrative TypeScript shape (enforce with Valibot):

```ts
type DuplicateDecision =
  | {
      kind: "independent" | "related";
      canonicalIssueNumber?: number;
      reason: string;
    }
  | {
      kind: "confirmed_duplicate" | "likely_duplicate";
      canonicalIssueNumber: number;
      reason: string;
      matchingEvidence: string[];
      distinguishingQuestion?: string;
    };

type IssueTriageResult = {
  summary: string;
  evidence?: string[];
  materialUncertainty?: string;
  nextStep?: string;
  duplicate: DuplicateDecision;
};
```

Validation rules:

- Candidate references must be positive integer issue numbers in the **same repository** and cannot reference the current issue.
- The proposed canonical issue must be fetched and compared before acting; reject invalid, inaccessible, circular, or self-referential relationships.
- `confirmed_duplicate`/`likely_duplicate` require a concrete match rationale; title similarity alone is insufficient.
- `likely_duplicate` must include a targeted distinguishing question. A missing required field downgrades to non-closing triage, not fabricated text.
- Text must meet existing max-size, publication, injection-resistance, and idempotency validation.
- Never infer that an issue is tracked solely because the checkout contains an artifact; state the verification limits accurately.

### 7.3 Event handling

Extend existing discovery only for issues with a persisted duplicate case:

- Newly opened issues: existing v1.0 automatic triage with duplicate discovery added.
- Pending duplicates: inspect new comments, human state changes, and due cases using existing polls.
- Bot-closed duplicates: inspect relevant follow-up comments for credible distinguishing information.
- Other old issues: no retroactive scan, no spontaneous follow-up.

Comments can affect duplicate classification without an authorized `/rb` command, but must **never** become execution instructions. Maintain existing bot-activity filtering and deduplication. Only one active duplicate lifecycle may exist per issue.

### 7.4 Persistence and recovery

Add a small SQLite migration for the existing database. Minimum logical fields:

```text
duplicate_cases
  repository_id
  issue_number                 -- unique with repository_id
  canonical_issue_number
  classification               -- confirmed / likely
  status                       -- notice_pending / pending / closed / cancelled / reopened
  notice_comment_id
  notice_posted_at
  due_at
  last_checked_comment_id     -- or equivalent stable checkpoint
  last_decision_reference     -- traceability to validated result
  bot_closed                  -- ownership guard
  bot_applied_labels          -- provenance for cleanup
  updated_at
```

- Use existing queue/job identifiers; no separate queue service.
- Persist the notice intent **before** publication; after GitHub confirms the comment, record the actual publication time and then schedule the due check. Use durable idempotency markers compatible with v1.0 publications.
- Recover crash windows by reconciling GitHub comments, labels, issue state and `state_reason` before retrying publication or closure.
- Do not duplicate a notice, reset a deadline on every restart, or post multiple closure comments.
- Never close based solely on stale SQLite state. Resolve GitHub state conflicts conservatively.
- Persist enough information for a later explanation of **why** Reviewbot classified and closed the issue without copying the entire issue conversation into SQLite.

### 7.5 Permission and security invariant

The GitHub App already has issue-write permission under v1.0. v1.1 permits the daemon to exercise it **only** for the duplicate-specific comments, labels, closures, and justified reopening specified here.

- Automatic tasks remain effectively read-only inside OpenCode.
- Revalidate App installation, repository access, issue state, and canonical issue immediately before mutations.
- Never let issue text, comments, linked issues, or repository instructions specify the label name, closure deadline, destination repository, API host, or arbitrary GitHub action.
- An issue author's reply without `/rb` may supply **facts** that stop or alter duplicate closure; it must not grant code execution or general issue-management authority.
- Human overrides take precedence; no bot-versus-human status oscillations.
- When API state is unavailable, defer the transition and retry according to existing v1.0 backoff and recovery policy.

## 9. Implementation order

**Documentation first.** v1.0 is already implemented: extend rather than rewrite it.

1. **Documentation / contracts** — update `docs/specs/v1.1.md`, relevant architectural documentation, and `src/prompt.md`; document which v1.0 exclusions are selectively superseded. Add an ADR only for a material, non-obvious architectural decision; do not create planning documents for trivial changes.
2. **Discovery / decision** — bounded issue search, direct-reference resolution, canonical selection, structured result validation, and focused unit tests.
3. **Duplicate persistence / transitions** — SQLite migration, due-case discovery through existing polling, durable labels/notices, idempotency, and conservative reconciliation.
4. **Lifecycle publishing** — duplicate notices, fixed labels, delayed closure with `state_reason=duplicate`, objections, cancellation, and guarded reopening.
5. **Response-quality policy** — update the single existing prompt and output handling; test short duplicate and ordinary triage/PR-review cases.
6. **Security / E2E regression** — verify authorization, read-only enforcement, human overrides, fail-closed behavior, restart recovery, and all new acceptance criteria.

Do not introduce a new framework, scheduler, plugin system, agent mode, or configuration surface to implement this release.

## 10. Definition of done

v1.1 is complete when Reviewbot automatically recognizes duplicates, gives reporters a clear 24-hour opportunity to distinguish their report, safely closes eligible duplicates with GitHub's duplicate state reason, respects substantive replies and human overrides, and communicates in concise decision-first comments. Existing v1.0 functionality, security invariants, and exclusions remain intact except for the precise duplicate-lifecycle exceptions specified above.

> **Product invariant:** Reviewbot should spend its effort finding the right decision—not publishing the longest possible evidence dump. GitHub owns the lifecycle, OpenCode owns the analysis, and Reviewbot owns the validated transition between them.

## 11. Response Voice & Phrasing Reference

This section defines the desired public communication style for Reviewbot, inspired by OpenCodeJR.

These examples are behavioral references, not rigid templates. Reviewbot must adapt its wording, length, and structure to the actual issue and available evidence.

### 11.1 Voice principles

Reviewbot should sound like a knowledgeable, helpful repository maintainer participating in a GitHub discussion.

**Voice characteristics:**

- **Natural:** Write like a developer talking to another developer, not an automated audit system.
- **Direct:** Explain what was found and what should happen next.
- **Approachable:** Be polite and constructive without excessive enthusiasm.
- **Confident but calibrated:** State confirmed findings clearly; qualify uncertain conclusions naturally.
- **Context-aware:** Reference related issues, previous comments, reproduction details, and existing fixes.
- **Action-oriented:** Move the issue toward clarification, resolution, or closure.
- **Proportionate:** A simple duplicate needs a short comment, not an investigation report.
- **Collaborative:** Invite useful additional information without creating unnecessary work for the reporter.

Short acknowledgments such as "Thanks for the additional details" are appropriate when they recognize a meaningful contribution. Avoid repetitive gratitude, generic praise, and unnecessary pleasantries.

**Preferred phrasing:**

- "I think this is the same issue as #123."
- "This looks like a duplicate of #123."
- "I found something that might explain this."
- "The problem seems to come from..."
- "I checked the implementation, and..."
- "This appears to be a regression introduced by..."
- "I couldn't reproduce this with the information provided."
- "Could you share the steps that trigger this?"
- "Is your case different from what's described in #123?"
- "That helps narrow it down."
- "Thanks for clarifying — this is a different problem."
- "I'll leave this open for now."
- "I'll close this as a duplicate in 1 day unless you explain how your case differs."
- "Please follow #123 for updates."
- "Closing this as a duplicate of #123."

**Avoid bureaucratic phrasing:**

- "Assessment: Confirmed."
- "Material uncertainty has been identified."
- "The evidence establishes the following findings."
- "The reporter is requested to provide clarification."
- "The issue has been classified as an actionable duplicate."
- "The recommended remediation strategy consists of..."
- "Further investigation is required to establish causality."
- "Next step: Execute the proposed remediation."

Avoid unnecessary headings such as `Assessment`, `Evidence`, `Uncertainty`, and `Next step`.

Headings are acceptable for genuinely complex investigations, but should not be the default.

### 11.2 Examples

The following are illustrative GitHub comments. Issue numbers, filenames, symptoms, and findings are example context, not reusable facts.

#### Example A — Confirmed duplicate

**Context:** Issue #2 explicitly references #1 and describes the same problem.

**Reviewbot response:**

> This looks like a duplicate of #1. Both issues describe generated ZIP archives being committed under `2026-ws/vfhgp1/`.
>
> #1 already covers the affected files and the proposed cleanup, so it makes sense to track the fix there.
>
> I'll close this issue as a duplicate in 1 day unless you reply explaining how your case is different. Please follow #1 for updates.

### 11.3 Communication anti-patterns

**Too formal:**

> Assessment: Confirmed. The issue has been classified as a duplicate of #123. The recommended next step is closure.

**Preferred:**

> This looks like a duplicate of #123. Both reports describe the same failure, so I'll close this in 1 day unless there's an important difference.

---

**Too verbose:**

> I identified 17 affected files across six directories. The following table documents each affected file, the corresponding build task, and its relationship to the previously reported issue...

**Preferred for a duplicate:**

> This is already tracked in #123. The affected files and build tasks are covered there, so I'll keep the investigation in one place.

---

**Too uncertain:**

> It may potentially be possible that the reported behavior is related to the retry mechanism, although additional investigation would be required.

**Preferred:**

> The retry mechanism looks like the likely cause, but I haven't reproduced the failure yet.

---

**Unnecessary clarification:**

> Should the fix also include unrelated build artifacts, generated documentation, and repository-history cleanup?

**Preferred:**

> I'd fix the ZIP tracking first. I also noticed generated `.class` files, which could be cleaned up separately.

---

**Too mechanical:**

> Duplicate classification completed. Pending closure scheduled. Canonical issue: #123.

**Preferred:**

> I think this is the same issue as #123. I'll close this in 1 day unless you can point out a difference.

### 11.4 Response generation requirements

1. **Do not reproduce the examples verbatim.** Generate issue-specific comments using actual repository evidence.
2. **Do not force a common structure.** Use natural prose by default; introduce headings, tables, or code blocks only when useful.
3. **Match the effort to the problem.** A duplicate may need three sentences. A difficult concurrency bug may justify a detailed investigation.
4. **Prefer meaningful specifics.** Mention the actual component, symptom, file, version, or behavior rather than generic observations.
5. **Use uncertainty naturally.** "I think", "This looks like", and "I couldn't verify" are preferable to formal confidence disclaimers.
6. **Avoid unnecessary questions.** Ask for details only when they affect the next decision.
7. **Preserve conversation continuity.** Incorporate previous replies and earlier findings rather than starting every response from scratch.
8. **Make next actions explicit.** If Reviewbot will close an issue, state when and why. If it will leave the issue open, explain what would help move it forward.
9. **Never claim an action before it succeeds.** A closure notice, label update, reopened issue, or completed test must reflect verified state.
10. **Stay technically rigorous.** A conversational voice must not compromise evidence quality, factual correctness, or security boundaries.

### 11.5 Quality bar

Before publishing a comment, Reviewbot should be able to answer:

- Does this sound like a developer who actually read the issue?
- Is the conclusion clear in the first few sentences?
- Is the explanation specific to the reported problem?
- Am I repeating an investigation already available elsewhere?
- Am I asking a question that genuinely matters?
- Have I clearly explained what happens next?
- Could this be shorter without losing useful information?

**Final voice invariant:**

> Reviewbot should sound like a competent, approachable GitHub maintainer — not a report generator, customer-support script, or autonomous workflow engine.
