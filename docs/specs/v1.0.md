# Reviewbot — v1 Product & Technical Specification

**Status:** Approved for implementation  
**Version:** 1.0  
**Date:** 2026-11-13  
**Target:** GitHub Enterprise Cloud (`*.ghe.com`) and GitHub.com  
**Runtime:** Bun / TypeScript  
**Architecture:** Local daemon + GitHub App + existing OpenCode V2 service

## 1. Product Definition

Reviewbot connects GitHub repositories to an existing OpenCode instance.

It provides two automatic capabilities:

1. **Issue triage:** Investigates newly opened issues and publishes evidence-based assessments, similar to OpenCodeJR.
2. **Pull request reviews:** Reviews new and updated pull requests and publishes actionable findings, similar to CodeRabbit.

Repository collaborators can also invoke Reviewbot through natural-language GitHub mentions to continue investigations, answer questions, or explicitly request code changes.

### Core principle

> Reviewbot is an integration layer, not an AI execution platform.

Reviewbot owns GitHub authentication, event discovery, authorization, durable job tracking, task dispatch, and publication.

OpenCode owns reasoning, tools, models, agents, project instructions, and session execution.

Reviewbot must never reimplement capabilities already provided by OpenCode.


Use the installed OpenCode V2 client contract. Pin a tested compatible client version and verify compatibility during startup.

### Deliberately excluded dependencies

- Effect
- Probot
- Express, Hono, or other persistent HTTP frameworks
- Prisma, Drizzle, or another ORM
- Redis or external queue systems
- Dedicated workflow or agent orchestration frameworks
- Docker or sandbox provisioning SDKs

Bun's built-in SQLite and HTTP facilities are sufficient.

### Responsibilities

**Reviewbot:**

- Authenticate as a GitHub App.
- Discover installed repositories.
- Poll GitHub for relevant changes.
- Authorize explicit instructions.
- Maintain a durable queue.
- Prepare isolated local workspaces.
- Dispatch tasks to OpenCode.
- Validate and publish results.
- Recover from interruptions.

**OpenCode:**

- Investigate issues.
- Analyze code and pull requests.
- Search documentation and repository context.
- Use its existing tools and subagents.
- Implement explicitly requested code changes.
- Return findings and execution results.

No separate agent runner, model registry, or workflow scheduler may be introduced.

## 4. GitHub Enterprise Support

### Required hosts

The GitHub host must be configurable.

Examples:

| Host           | REST API                   |
| -------------- | -------------------------- |
| `github.com`   | `https://api.github.com`   |
| `acme.ghe.com` | `https://api.acme.ghe.com` |

GHE.com must not be treated as GitHub Enterprise Server.

The host URL must be validated. Never construct network destinations from untrusted issue or PR content.

### GitHub App registration

Command:

```bash
reviewbot setup
```

The setup wizard must:

1. Prompt for the GitHub host and organization.
2. Generate the GitHub App manifest.
3. Start a temporary loopback callback listener.
4. Open the GitHub App manifest registration flow.
5. Receive and validate the callback state and temporary code.
6. Exchange the code for App credentials through the correct host-specific API.
7. Store the required credentials securely.
8. Direct the user to install the App on selected repositories.
9. Verify installation access and permissions.
10. Initialize repository monitoring cursors without processing historical work.

The setup wizard must not require a permanent publicly reachable endpoint.

Manifest registration must use an **organization-owned GitHub App**, not an enterprise-owned App. Enterprise-owned App manifests are not supported by the documented flow.

Use an inactive webhook configuration:

```json
{
  "hook_attributes": {
    "url": "https://example.invalid/reviewbot/webhook",
    "active": false
  },
  "default_permissions": {
    "metadata": "read",
    "contents": "write",
    "issues": "write",
    "pull_requests": "write"
  },
  "default_events": [],
  "public": false,
  "request_oauth_on_install": false
}
```

The webhook URL is a required manifest field but is not used at runtime. The complete manifest must also include the App name, homepage URL, and temporary registration redirect URL.

The actual GHE.com manifest and loopback callback behavior must be validated against a test organization before release.

If organizational policy prohibits App creation or installation, setup must report the restriction instead of attempting to bypass it.

### Authentication

Use GitHub App installation access tokens for all repository API operations.

- No personal access tokens.
- No dependency on `gh auth`.
- Refresh installation credentials when needed.
- Revalidate installation access before publishing.
- Request narrower token permissions where supported.
- Never put tokens into prompts, logs, Git remote URLs, or persistent repository configuration.

Reviewbot owns GitHub publishing. OpenCode must not receive installation credentials for read-only tasks.

For explicit implementation tasks, the daemon performs authenticated pushes and PR creation after verifying the generated changes.

## 5. Event Discovery

### Polling

Use outbound REST API polling.

Default interval: **60 seconds**.

Polling must:

- Enumerate active App installations and their accessible repositories.
- Discover new issues and PRs.
- Detect PR head changes and draft-to-ready transitions.
- Discover new issue/PR conversation comments.
- Discover new inline PR review comments and replies.
- Recognize explicit mentions of the installed App.
- Exclude the bot's own activity.
- Persist independent checkpoints for each relevant event source.

Use conditional requests and bounded overlapping polling windows where supported. Checkpoint advancement must not skip events when API calls or pagination fail.

Respect pagination, rate limits, `Retry-After`, and GitHub's polling guidance.

### Initial synchronization

When a repository is first discovered:

- Establish its current observation baseline.
- Do not retroactively process existing issues and PRs.
- Begin automatic processing only for subsequent qualifying changes.

A newly installed repository must follow the same rule.

### Trigger contract

| Trigger                     | Action                |
| --------------------------- | --------------------- |
| New issue                   | Initial triage        |
| New non-draft PR            | Initial code review   |
| New commits to non-draft PR | Incremental review    |
| Draft PR becomes ready      | Initial review        |
| Authorized mention          | Natural-language task |
| Bot-generated event         | Ignore                |

Editing titles, labels, descriptions, or unrelated metadata must not automatically produce another review.

No arbitrary event rules, labels-as-triggers, schedules, or workflow definitions.

## 6. Issue Triage

For every newly opened issue, Reviewbot must:

1. Read the issue title and description.
2. Inspect relevant repository code and documentation.
3. Retrieve relevant existing issue or PR context when useful.
4. Identify what can be established from the available evidence.
5. Separate verified facts from hypotheses.
6. Ask targeted clarification questions only when necessary.
7. Publish one concise GitHub issue comment.

The response should contain:

- A short assessment.
- Relevant findings and evidence.
- Any material uncertainty.
- A specific next step or clarification question when applicable.

It must not:

- Automatically modify source code.
- Change issue labels, assignees, status, milestones, or projects.
- Close issues.
- Claim a root cause without sufficient evidence.
- Repeatedly comment when nothing meaningful has changed.

Subsequent responses require an authorized mention.

## 7. Pull Request Reviews

### Automatic behavior

Review new and updated non-draft PRs, excluding PRs authored by Reviewbot itself.

For each review:

1. Capture the PR head SHA and base reference.
2. Retrieve the diff and relevant context.
3. Inspect affected files and surrounding implementation.
4. Identify concrete defects introduced by the changes.
5. Validate findings against available evidence.
6. Retrieve previous bot findings to avoid repetition.
7. Validate the output and GitHub diff locations.
8. Recheck the current head SHA.
9. Publish a GitHub `COMMENT` review.

### Review quality

Focus on:

- Correctness and behavioral regressions.
- Relevant edge cases.
- Security vulnerabilities.
- Error handling.
- Concurrency and state management.
- Significant performance problems.
- Clear violations of established project invariants.

Avoid:

- Stylistic nitpicks.
- Subjective preferences.
- Speculative vulnerabilities without a plausible failure scenario.
- Generic praise.
- Repeating findings already raised.
- Unnecessary file-by-file descriptions.

### Publishing

A review contains:

- One concise summary.
- Inline findings for confirmed problems on changed lines.
- Severity and a concrete explanation of impact.
- Summary-level findings when no valid changed-line mapping exists.

Publish a short review even when no actionable issues are found.

Always use `COMMENT` review state. Never automatically approve or request changes.

Do not produce Check Runs or commit statuses.

### Incremental reviews

When new commits arrive:

- Review changes since the last reviewed commit.
- Retain sufficient broader context to detect regressions.
- Suppress duplicate findings.
- Publish a new review for the new head SHA.
- Preserve previous GitHub reviews as historical records.

If the PR head changes while a review is running, discard the obsolete result and queue review of the new head.

Never post an outdated review as the current assessment.

## 8. Natural-Language Interaction

> **Superseded by v1.1:** explicit tasks now trigger on the literal `/rb` command. The examples below describe the original v1.0 trigger and remain for baseline context.

Reviewbot must recognize mentions using its actual installed GitHub App identity.

Examples:

```text
@reviewbot can you investigate the root cause?

@reviewbot is this actually a regression?

@reviewbot can you reproduce this?

@reviewbot fix the issue and open a draft PR.

@reviewbot please address the findings here.
```

The examples are illustrative, not a command grammar.

### Supported locations

- Issue comments.
- PR conversation comments.
- Inline PR review discussions.

Follow-up replies must be contextual. Inline review replies should remain in the relevant discussion thread.

Replies without an explicit mention must not trigger execution.

### Authorization

Only repository collaborators with **write access or higher** may trigger explicit tasks.

Permission checks must use GitHub's repository permission information, not author association labels or an internal username list.

Unknown or insufficient permissions deny execution.

Automatic triage and reviews still apply to contributions from users without write access.

### Session continuity

Each issue or PR has an associated conversational OpenCode session.

- Authorized follow-ups reuse the existing session.
- New automatic PR reviews use fresh review contexts.
- Session IDs persist across daemon restarts.
- Sessions remain visible through normal OpenCode interfaces.
- OpenCode owns session history and compaction.

Reviewbot must not implement its own conversational memory system.

## 9. Explicit Code Changes

Code modification requires a clear, explicit instruction from an authorized collaborator.

### Issue-based fixes

1. Prepare an isolated worktree from the target repository's default branch.
2. Ask OpenCode to implement the requested change.
3. Inspect the resulting changes and verification results.
4. Commit the authorized changes.
5. Push an isolated branch using the App installation credentials.
6. Open a draft PR against the default branch.
7. Link the original issue.

### PR-based fixes

1. Fetch the original PR's current head.
2. Create a separate local branch from that commit.
3. Ask OpenCode to implement the requested correction.
4. Commit and push to a new branch in the target repository.
5. Create a separate draft PR targeting the original PR's base.
6. Explain that the draft includes the original PR's changes.
7. Link the original PR.

Never modify a contributor's original branch in v1.

If repository rules, fork access, or other restrictions prevent a valid draft PR, report the blocker. Do not bypass branch protection or silently change the operation.

### Prohibited actions

- Automatic fixes without a maintainer request.
- Automatic merges.
- Automatic approvals.
- Force-pushing.
- Changes to unrelated repositories.
- Changing GitHub administration settings.
- Executing unauthorized CI repair workflows.

## 10. OpenCode Integration

Use `@opencode/client` exclusively.

### Connection

- Discover the existing OpenCode V2 background service with `Service.discover()`.
- Alternatively, connect to a configured, authenticated OpenCode endpoint.
- Verify the server is reachable and compatible.
- Do not spawn, restart, replace, or manage the OpenCode service.

If OpenCode is unavailable, leave jobs queued and report the condition through local diagnostics.

### Prompts

Use one versioned instruction file:

```text
src/prompt.md
```

The prompt must cover:

- Investigation and evidence standards.
- Conservative code review.
- Explicit implementation boundaries.
- Verification and reporting.
- Concise GitHub communication.
- Treatment of untrusted content.

Use session-specific instruction entries supported by the client, retaining native OpenCode instructions.

Task requests may contain contextual data such as issue text, PR URLs, head SHA, and requested action. They must not introduce separate agent personalities or system prompts.

OpenCode's existing agents and subagents remain available subject to effective permissions.

### Structured results

Require machine-readable output appropriate to the task and validate it with Valibot.

For example:

```ts
type ReviewResult = {
  summary: string;
  findings: Array<{
    path: string;
    line: number;
    side: "LEFT" | "RIGHT";
    severity: "low" | "medium" | "high";
    message: string;
  }>;
};
```

The schema expresses publication data, not an agent mode.

The daemon must validate:

- Result structure.
- Referenced file paths.
- Diff line mappings.
- Current head SHA.
- Maximum output size.
- Publication eligibility.

Do not publish malformed output or invent replacement findings.

## 11. Security Boundary

Security constraints are mandatory and must not be weakened to simplify implementation.

### Threat model

Untrusted inputs include:

- Issue descriptions.
- PR descriptions and comments.
- Contributor source changes.
- Repository files and project instructions in untrusted branches.
- Tool and model output.

These inputs may contain prompt injection, malicious commands, or attempts to expose local credentials.

### Automatic tasks

Automatic triage and reviews must operate in an effectively read-only configuration.

The permission boundary must deny:

- File edits.
- Shell and process execution.
- Code Mode execution capable of bypassing restrictions.
- Unauthorized MCP or plugin tools.
- Access outside the assigned workspace.
- GitHub credential access.
- Publishing directly from the model.

Read-only restrictions must be enforced through the available runtime and permission mechanisms, not merely through the system prompt.

**Release gate:** Verify that the existing OpenCode V2 server can enforce these restrictions for Reviewbot tasks without weakening its other sessions. If this is not possible, automatic processing of untrusted content must be disabled rather than silently executed with the user's unrestricted permissions.

Git worktrees do not constitute an execution sandbox.

### Requested implementations

Authorized write tasks may modify their isolated workspace.

Project scripts and tests may execute only when the code is trusted or a suitable pre-existing isolated execution environment is available.

If verification cannot be performed safely, report it explicitly.

No automatic sandbox installation or provisioning is included.

### Credentials

- App private keys are readable only by the local operator.
- Short-lived installation tokens are never persisted.
- Do not store tokens in Git remotes.
- Do not pass tokens into OpenCode prompts or task environments.
- The daemon performs authenticated Git pushes separately from OpenCode execution.
- Logs must redact credentials and sensitive paths where appropriate.

### Output authority

Only the daemon may publish comments, reviews, commits and PRs using installation credentials.

It must revalidate authorization and relevant GitHub state immediately before write operations.

## 12. Durability and Recovery

Use one SQLite database with WAL enabled.

### Persistent state

Keep only:

- Installation and repository observation state.
- Polling checkpoints.
- GitHub-to-OpenCode session mappings.
- Queued and running jobs.
- Retry metadata.
- Reviewed commit SHAs.
- Publication identifiers and idempotency markers.

Avoid storing entire GitHub conversations or OpenCode session histories.

### Job lifecycle

```text
queued
   |
   v
running
   |
   +------> retry scheduled
   |              |
   |              v
   |            queued
   |
   +------> failed
   |
   v
published / completed
```

Use a single global worker. No parallel OpenCode tasks in v1.

### Reliability rules

- Persist a job before dispatch.
- Deduplicate using stable event identifiers and task-specific keys.
- Resume or reconcile interrupted jobs after restart.
- Treat publication as complete only when GitHub confirms it.
- Use identifiable publication markers to detect already-posted results.
- Check GitHub for an existing publication before retrying after an ambiguous failure.
- Cancel or safely interrupt timed-out execution where supported.
- Retry transient errors at most twice.
- Do not retry permanent authorization or validation failures.
- Preserve rate-limit backoff and cursor integrity.
- Do not create bot feedback loops.

Default task limits:

| Task                    | Timeout    |
| ----------------------- | ---------- |
| Automatic triage        | 15 minutes |
| Automatic review        | 15 minutes |
| Explicit implementation | 60 minutes |

Expired or revoked installations must halt further writes for their repositories.

## 13. CLI

Expose exactly four commands.

```bash
reviewbot setup
reviewbot run
reviewbot status
reviewbot doctor
```

### `setup`

Configure GitHub App registration, credentials, installation access, and monitoring baseline.

### `run`

Start the polling daemon and job worker.

The process runs in the foreground. The operating system manages background execution and restarts.

### `status`

Show:

- Current configured GitHub host.
- OpenCode connectivity.
- Active installation count.
- Repository count.
- Last successful poll.
- Queue depth and active job.
- Recent failures.

### `doctor`

Validate:

- Bun and Git availability.
- GitHub connectivity and App credentials.
- Installation and repository permissions.
- OpenCode service compatibility.
- Required security restrictions.
- SQLite accessibility.

`doctor` is diagnostic. It must not automatically install tools or rewrite development environments.

## 14. Configuration and Storage

One global configuration file.

Example:

```json
{
  "github": {
    "host": "acme.ghe.com"
  },
  "polling": {
    "intervalSeconds": 60
  },
  "opencode": {
    "url": null,
    "model": null
  }
}
```

A null OpenCode URL means discover the existing registered local service. A null model
means use OpenCode's default model. A configured model uses the `providerID/modelID` form
and is passed to Reviewbot sessions; Reviewbot does not manage providers or route models.

Validate configuration using Valibot.

Use conventional per-user configuration and data locations:

```text
Configuration:
  ~/.config/reviewbot/config.json

Data:
  ~/.local/share/reviewbot/

Credentials:
  ~/.local/share/reviewbot/credentials/

Database:
  ~/.local/share/reviewbot/reviewbot.db

Repositories/worktrees:
  ~/.local/share/reviewbot/workspaces/
```

On Windows, resolve equivalent user-local directories rather than assuming POSIX paths.

Use restrictive file permissions and Windows ACLs for sensitive credentials.

No repository-specific Reviewbot configuration files.

Model selection and development settings remain primarily under OpenCode's control.
Reviewbot may pass one optional configured model identifier (`provider/model`) to the
sessions it creates. It does not route models per task, manage provider credentials, or
select agents.

## 16. Explicit Non-Goals

The following are outside v1 and must not be implemented without a separate product decision.

### AI and agents

- Custom agents or named modes.
- Agent selection or model routing.
- Custom multi-agent orchestration.
- Prompt-template systems.
- Configurable review personalities.
- Model provider management.
- An additional conversational memory system.

### GitHub automation

- Automatic fixing or CI repair.
- Merging or approving PRs.
- Label and assignee management.
- Milestones, projects, and issue closure.
- Review-thread resolution automation.
- Dependency update automation.
- Arbitrary event triggers and schedules.
- Multi-repository change orchestration.

### CodeRabbit-style extras

- Review scores.
- Architectural diagrams.
- PR walkthroughs.
- File-by-file summaries.
- AI-generated test suites.
- Standalone vulnerability scanning.
- Feature parity with CodeRabbit.

### Product and infrastructure

- Hosted SaaS.
- Web dashboard.
- Desktop interface.
- Browser notifications.
- Multiple operator accounts.
- Distributed workers.
- Parallel job execution.
- Webhook hosting and tunnels.
- Docker, VM, or sandbox provisioning.
- Cloud infrastructure management.
- Redis or external databases.
- General-purpose workflow automation.
- Metrics servers, cost dashboards, or tracing platforms.
- Automatic update systems.
- Custom service supervision.

### Configuration

- Per-repository Reviewbot policies.
- A workflow DSL.
- Custom trigger expressions.
- Arbitrary automations.
- Multiple simultaneous GitHub hosts.
- Custom GitHub bot identities or aliases.

## 17. Acceptance Criteria

A dedicated repository on `acme.ghe.com` must pass these end-to-end tests before production use.

| ID    | Test                        | Expected result                                       |
| ----- | --------------------------- | ----------------------------------------------------- |
| AC-01 | Manifest setup              | Organization-owned App registered and installed       |
| AC-02 | GHE.com connectivity        | Correct host-specific API and installation auth       |
| AC-03 | Initial synchronization     | Historical issues and PRs ignored                     |
| AC-04 | New issue                   | One evidence-based triage comment                     |
| AC-05 | New non-draft PR            | One review with inline findings when appropriate      |
| AC-06 | Draft becomes ready         | Initial review created                                |
| AC-07 | New PR commit               | Incremental review without duplicate findings         |
| AC-08 | Clean PR                    | Short review without fabricated findings              |
| AC-09 | Issue mention               | Existing conversational session reused                |
| AC-10 | PR inline mention           | Relevant discussion receives a reply                  |
| AC-11 | Authorized fix              | Isolated draft PR created                             |
| AC-12 | Unauthorized fix            | No code or GitHub changes                             |
| AC-13 | Daemon restart              | Jobs recovered without duplicate publication          |
| AC-14 | OpenCode unavailable        | Jobs remain queued                                    |
| AC-15 | Installation revoked        | Processing and publishing halted                      |
| AC-16 | PR head changes mid-review  | Obsolete result not published                         |
| AC-17 | Malicious issue/PR content  | Unauthorized tools and external file access blocked   |
| AC-18 | No safe execution boundary  | Untrusted automatic task fails closed                 |
| AC-19 | GitHub rate limiting        | Backoff observed, no missed events                    |
| AC-20 | Credential exposure attempt | Secrets absent from output, logs and OpenCode context |

Automated unit tests should cover polling cursors, authorization, state transitions, schema validation, idempotency and error handling.

Integration tests must use actual GitHub App installation authentication. Mocked unit tests do not establish GHE.com compatibility.

## 18. Implementation Order

### Phase 1 — Foundation

- Bun project and Commander CLI.
- Valibot configuration.
- GitHub App manifest setup.
- Octokit installation authentication.
- Existing OpenCode service discovery.
- Diagnostics and logging.

**Exit:** `setup` and `doctor` work against `acme.ghe.com`.

### Phase 2 — Automatic issue triage

- SQLite job queue.
- Polling and initial synchronization.
- Repository workspace handling.
- OpenCode session dispatch.
- Read-only permission enforcement.
- Issue triage publication.

**Exit:** New issues receive reliable, evidence-based comments without unauthorized execution.

### Phase 3 — PR reviews

- PR discovery and head tracking.
- Review output validation.
- Changed-line mapping.
- Inline review publication.
- Incremental reviews.
- Duplicate suppression and stale-result handling.

**Exit:** New and updated PRs receive reliable, actionable reviews.

### Phase 4 — Conversations and fixes

- Authorized natural-language mentions.
- Session continuity.
- Explicit isolated implementation.
- Authenticated Git push.
- Draft PR creation.

**Exit:** Maintainers can request investigations and fixes through GitHub discussions.

### Phase 5 — Hardening and release

- Restart and interruption recovery.
- Installation revocation handling.
- Rate-limit handling.
- Security regression tests.
- Windows/Linux integration testing.
- macOS compatibility checks.
- Acceptance suite on GHE.com.

**Exit:** All acceptance criteria pass.

## 19. Scope Enforcement

Every proposed change must meet at least one condition:

1. It implements an approved acceptance criterion.
2. It is necessary for correctness, security, or recovery.
3. It materially simplifies the implementation without expanding product behavior.

Otherwise, it is out of scope.

Avoid speculative abstractions, optional platforms, convenience features, and unrelated refactoring.

A new feature must not be justified solely because its implementation is technically straightforward.

**Final product invariant:**

> Reviewbot connects GitHub to OpenCode. GitHub owns collaboration, OpenCode owns intelligence, and Reviewbot owns only the integration between them.
