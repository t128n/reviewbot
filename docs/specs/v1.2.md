# Reviewbot — v1.2 Product & Technical Specification

**Status:** In progress  
**Version:** 1.2  
**Date:** 2026-11-14  
**Baseline:** `docs/specs/v1.1.md` (implemented; external GHE.com acceptance pending credentials)  
**Target:** GitHub.com and GitHub Enterprise Cloud (`*.ghe.com`)  
**Runtime:** Existing Bun / TypeScript daemon, GitHub App, SQLite, `issue-graph`, and OpenCode V2 integration

## 1. Product decision

**v1.2 replaces Reviewbot's token-overlap duplicate discovery with `issue-graph` graph
crawling, classification, heat prioritization, and PR overlap analysis.**

This improves issue triage by surfacing structural GitHub relationships—cross-references,
connected events, closing PRs, superseded PRs, reverse mentions (`mentionedBy`), and
overlapping open PRs—while preserving every v1.1 security boundary, duplicate lifecycle
rule, and daemon-only GitHub write model.

### Normative relationship to v1.1

This document is an **additive v1.2 specification** over `docs/specs/v1.1.md`. All v1.0 and
v1.1 requirements remain in force **except the explicit discovery update below**.

| v1.1 provision                                | v1.2 change                                                                                                                               |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| §3.1: Token-overlap scoring and REST comments | Replaced by `issue-graph` (`crawl`, `classify`, `fillMentionedBy`, `prioritize`, `score`, `fileOverlaps`) over an Octokit GraphQL adapter. |

**Unchanged:** single worker, outbound polling, existing OpenCode service, read-only
automatic agent execution, GitHub App authentication, collaborator authorization for
explicit tasks, duplicate lifecycle state machine, 24-hour window, two-label policy
(`pending close`, `duplicate`), and daemon-only GitHub writes.

## 2. Scope and non-goals

### In scope

- Integrating the `issue-graph` library into `src/duplicate-discovery.ts` using an
  Octokit-backed `GhTransport` (`POST /graphql` + `GET /search/issues`).
- Crawling the reference graph seeded from the current issue, explicit same-repository
  references, up to 3 bounded repository search queries, and recent repository issues.
- Running `classify`, `fillMentionedBy`, `prioritize` / `score`, and `fileOverlaps` on
  the crawled graph.
- Passing structured graph metadata (`kind`, `depth`, heat `score`, `verdict`, `flags`,
  `edges`, `mentionedBy`, and PR `fileOverlaps`) alongside candidate bodies and comments
  to the OpenCode triage session.

### Explicitly out of scope

- Using `issue-graph/transport/shell` (`gh` CLI) or `issue-graph/transport/http`
  (hardcoded `api.github.com` `fetch`).
- Passing GitHub tokens, GraphQL credentials, or `issue-graph` CLI/skills into OpenCode
  sessions.
- Cross-repository duplicate management or closing issues in external repositories.
- Changing PR review permissions, auto-merging, or expanding managed labels beyond
  `pending close` and `duplicate`.

## 3. Graph-based duplicate discovery

### 3.1 Seed collection and bounded crawl

For each initial issue triage, the daemon collects seeds in the installed repository:

1. The current issue (`owner/repo#number`).
2. Up to **10** explicit same-repository issue/PR references extracted from the current
   issue body and comments.
3. Up to **3** bounded repository search queries (title terms, body terms, and closed-issue
   body terms) via `GitHub.searchIssues`.
4. Recent repository issues via `GitHub.listRecentIssues` when additional seeds are needed.

The daemon runs `issue-graph`'s `crawl` with bounded parameters:

- `maxDepth: 1`
- `maxNodes: 40`
- `hubThreshold: 12`
- `concurrency: 4`
- `primaryRepo: { owner, repo }`

Nodes are fetched via `GitHub.graphql` (`NODE_QUERY`), which retrieves node metadata,
body, up to 100 comments, timeline cross-references/connections, closing-issue links,
reaction/participant heat, and PR file lists in one query per node.

If search or recent-issue listing fails, discovery degrades gracefully to the seeds and
graph nodes already available and marks `searchUnavailable` / `recentUnavailable` so the
triage prompt warns OpenCode that candidate coverage may be incomplete. Explicit
references that return `NOT_FOUND` are recorded in `unresolvedReferences` without
inventing candidates.

### 3.2 Classification, ranking, and output bounds

After `crawl`, the daemon runs:

1. `classify(nodes)` to tag structural verdicts (such as `superseded` open PRs) and
   triage flags.
2. `fillMentionedBy(nodes)` to populate reverse attribution.
3. `prioritize(nodes, now)` and `score(...)` to compute discussion-heat scores across
   open and closed/merged same-repository nodes.
4. `fileOverlaps(nodes)` to detect open PR pairs touching shared source files.

Candidates are filtered to fetched same-repository nodes (excluding the current issue),
sorted by explicit reference first, then shallower `depth`, higher `issue-graph` heat
`score`, earlier `createdAt`, and lower `number`, and capped at **20** candidates.

### 3.3 Triage prompt integration

`src/worker.ts` includes `issue-graph` context in the triage prompt for OpenCode:

- Candidate kind (`Issue` or `PullRequest`), state, graph `depth`, heat `score`,
  `verdict`, `flags`, `edges`, and `mentionedBy`.
- Overlapping open PR pairs from `fileOverlaps`, when present.
- Existing candidate title, creation timestamp, body, and relevant comments.

OpenCode's output remains advisory (`TriageResultSchema`); all canonical verification,
24-hour grace periods, label provenance, and closure/reopening decisions remain enforced
by the daemon under `docs/specs/v1.1.md`.
